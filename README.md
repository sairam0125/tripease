# TripEase - one-stop travel booking

Search, compare and book **flights, trains, buses, hotels and resorts** in one app, with
**price graphs**, **AI price insights ** and a **travel chatbot**.

**Stack:** Java 17 · Spring Boot 3 (Web, Data JPA, Security, Validation) · MySQL · JWT · React 18 (Vite) · Recharts · OpenAI API

> **Demo data notice:** there is no real airline/railway/bus supplier behind this project. Cities, schedules, fares and
> availability are generated by a deterministic pricing engine, and payment is simulated. See
> [Going live](#going-live-with-real-data).

## Features

| Area | What it does |
|---|---|
| Search | Flights, trains, buses (city to city, by date) and hotels/resorts (city, check-in/out, rooms). 12 Indian cities seeded. |
| Price graph | For any fare or hotel: price for every day around your date, with your date and the cheapest date highlighted. |
| AI insight | GPT-3.5 turns the price facts into a short "book now or shift dates" tip (cached 30 min). Falls back to rules without an API key. |
| Chatbot | Understands cities, mode, date and budget in plain English, fetches live options from the DB, and answers with one-tap search buttons. |
| Booking | Traveller details, mock payment, booking reference, "My trips" page and cancellation. |
| Auth | Register/login with BCrypt-hashed passwords and JWT (stateless). |
| Safety | Server-side price recalculation, row locking against overbooking, input validation, CORS allow-list, rate-limited AI endpoints. |

## Architecture

```
React (Vite)  --HTTPS/JSON-->  Spring Boot REST API  --JPA-->  MySQL
   |                              |  Controller -> Service -> Repository
   | JWT in Authorization header  |  JwtAuthFilter, SecurityConfig, GlobalExceptionHandler
   |                              +--> PricingService (demand-based pricing, used everywhere)
   |                              +--> InsightService / ChatService --> OpenAiClient --> OpenAI (groq llama-3.1)
   +-- Recharts price graph, chat widget, protected routes
```

```
tripease/
├── backend/                Spring Boot API
│   └── src/main/java/com/tripease/
│       ├── config/         SecurityConfig (JWT, CORS)
│       ├── controller/     Auth, Catalog, Price, Ai, Booking, Health
│       ├── service/        PricingService, CatalogService, BookingService, AuthService,
│       │                   InsightService, ChatService, OpenAiClient, RateLimiter
│       ├── model/          JPA entities (User, City, Trip, Hotel, Booking + enums)
│       ├── repository/     Spring Data repositories
│       ├── dto/            Request/response records
│       ├── security/       JwtService, JwtAuthFilter
│       ├── seed/           DataSeeder (demo cities, trips, hotels)
│       └── exception/      ApiException + GlobalExceptionHandler
├── frontend/               React app (pages, components, context, hooks)
├── docker-compose.yml      MySQL + backend for local use
└── render.yaml             optional Render blueprint
```

## Run locally

Prerequisites: JDK 17+, Maven 3.9+, Node 18+. (MySQL 8 or Docker for the MySQL options.)

**Option A - fastest (no MySQL, in-memory H2)**
```bash
cd backend
mvn spring-boot:run -Dspring-boot.run.profiles=h2
# new terminal
cd frontend
cp .env.example .env
npm install
npm run dev            # http://localhost:5173
```

**Option B - MySQL installed locally**
```bash
# create nothing by hand: the app creates the `tripease` database if it does not exist
cd backend
DB_USERNAME=root DB_PASSWORD=your_password mvn spring-boot:run
```

**Option C - Docker (MySQL + API)**
```bash
docker compose up --build       # API on http://localhost:8080
cd frontend && npm install && npm run dev
```

Tables are created automatically (`ddl-auto=update`) and the demo data is seeded on first start.

### Enable GPT-3.5 (optional)
```bash
export OPENAI_API_KEY=sk-...          # never commit this
mvn spring-boot:run -Dspring-boot.run.profiles=h2
```
Without a key everything still works: insights and the chatbot use rule-based answers. In the UI you can tell which
is active: AI answers say "Written by groq llama-3.1", rule answers say "Calculated from fare trends".

### Environment variables (backend)

| Variable | Default | Purpose |
|---|---|---|
| `DB_URL` | local MySQL `tripease` | JDBC URL |
| `DB_USERNAME` / `DB_PASSWORD` | `root` / `root` | DB credentials |
| `JWT_SECRET` | dev value | **Set a long random string (32+ chars) in production** |
| `CORS_ORIGINS` | `http://localhost:5173` | Comma-separated allowed front-end origins (wildcards ok: `https://*.vercel.app`) |
| `OPENAI_API_KEY` | empty | Enables GPT-3.5 |
| `OPENAI_MODEL` | `gpt-3.5-turbo` | Change the model without code changes |

Frontend: `VITE_API_URL` (backend base URL).

## API

| Method & path | Auth | Description |
|---|---|---|
| `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/auth/me` | - / - / JWT | Accounts |
| `GET /api/cities` | - | Cities for dropdowns |
| `GET /api/trips/search?mode=FLIGHT&from=Hyderabad&to=Goa&date=2026-10-10` | - | Flights/trains/buses with price and seats for the date |
| `GET /api/trips/{id}?date=` | - | One trip |
| `GET /api/hotels/search?city=Goa&checkIn=&checkOut=&type=RESORT` | - | Hotels/resorts with nightly and total price |
| `GET /api/prices/trips/{id}?date=` · `/api/prices/hotels/{id}?date=` | - | Price series for the graph |
| `GET /api/ai/insight?kind=TRIP&id=1&date=` | - | AI (or rule-based) price advice |
| `POST /api/ai/chat` `{message, history[]}` | - | Chatbot reply + one-tap search suggestions |
| `POST /api/bookings` · `GET /api/bookings` · `POST /api/bookings/{id}/cancel` | JWT | Book, list, cancel |
| `GET /api/health` | - | Health check |

Try it: `curl "http://localhost:8080/api/trips/search?mode=FLIGHT&from=Hyderabad&to=Goa&date=<a-future-date>"`

Chatbot examples: *"Cheapest way from Hyderabad to Goa this weekend under 5000"*, *"Resorts in Goa under 9000"*,
*"Train from Chennai to Bengaluru tomorrow"*, *"Where can I go from Hyderabad under 2500?"*

## Deployment (all free tiers)

Free plans and limits change, so check each provider's current terms. Suggested combination:

**1. MySQL - Aiven free MySQL** (or any hosted MySQL such as TiDB Cloud or Railway)
- Create a free MySQL service and copy host, port, user and password.
- JDBC URL: `jdbc:mysql://<host>:<port>/defaultdb?sslMode=REQUIRED`

**2. Backend - Render (Docker web service)**
1. Push this repo to GitHub (below).
2. Render → New → Web Service → pick the repo. Set **Root Directory** `backend`, **Runtime** Docker, **Instance type** Free.
3. Environment variables: `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `JWT_SECRET` (long random string),
   `CORS_ORIGINS` (fill in after step 3), optional `OPENAI_API_KEY`.
4. Health check path: `/api/health`. Deploy. Your API URL looks like `https://tripease-api.onrender.com`.
   Free instances sleep after ~15 minutes idle, so the first request can take 30-60 seconds; the UI shows loading
   skeletons and a retry button meanwhile.

**3. Frontend - Vercel (or Netlify)**
1. Vercel → Add New Project → import the repo. **Root Directory** `frontend`, framework Vite (auto-detected).
2. Environment variable `VITE_API_URL` = your Render URL (no trailing slash). Deploy.
3. Go back to Render and set `CORS_ORIGINS` to your Vercel URL, e.g. `https://tripease.vercel.app` (redeploys the API).

## How to explain this project (interview notes)

- **Layered backend:** controllers stay thin, business rules live in services, repositories talk to MySQL via JPA.
- **Auth:** BCrypt password hashing, stateless JWT checked in a filter, protected routes on the React side.
- **One pricing engine:** search, graphs, AI tips and checkout all call `PricingService`, so numbers always agree.
  The booking amount is recalculated on the server, never trusted from the browser.
- **Concurrency:** booking takes a pessimistic row lock on the trip/hotel, so two users cannot buy the last seat.
- **AI, done responsibly:** the app computes facts (price series, cheapest day, expected rise) and GPT only phrases
  the advice. The chatbot retrieves live options from the DB first ("retrieval + generation"), so it cannot invent
  fares. Client-supplied "system" messages are dropped to limit prompt injection, and AI endpoints are rate-limited.
- **Resilience:** with no key or if OpenAI is down, rule-based answers keep the UI working.
- **Frontend:** React Router, Context for auth, Axios interceptors for JWT and expiry, Recharts for graphs,
  responsive CSS with accessible controls.
- **Honest limitations:** demo data, simulated payment, in-memory rate limiter and cache (single instance).

## Going live with real data

Replace the demo seed and `PricingService` with a supplier integration (for example an aggregator API such as Amadeus
for flights). Keep the same DTOs so the frontend does not change. Add a real payment gateway with webhooks, email
confirmations, and move the cache and rate limiter to Redis if you run more than one instance.
